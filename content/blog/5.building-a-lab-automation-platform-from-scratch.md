# Building a Lab Automation Platform From Scratch

Modern biotech is racing toward fully closed-loop wet labs — machines running experiments end-to-end with minimal human intervention. At [Adaptyv Bio](https://www.adaptyvbio.com/), a protein engineering company, that meant orchestrating robot arms, liquid handlers, incubators, and analyzers into a single automated pipeline.

I was in charge of building the software fundation for automating the whole lab: the scheduler, the driver plugin, the CLI tooling, the workflow builder, and the real-time dashboard. Here's how.

## The architecture

I went with a **microservices approach**. Each piece of lab equipment gets its own **driver** — a small HTTP service that speaks to the hardware — and a central **scheduler** orchestrates everything.

::mermaid
---
code: |
  graph TD
    S[Scheduler<br/>FastAPI] --> R[Robot Arm<br/>Driver]
    S --> F[Fridge<br/>Driver]
    S --> L[Liquid Handler<br/>Driver]
    S --> P[Peeler<br/>Driver]
    S --> I[Incubator<br/>Driver]
    S --> H[Hamilton<br/>Driver]
---
::

This wasn't just a technical decision — it was an organizational one. By defining a clear contract (expose an OpenAPI spec, advertise via mDNS, follow the endpoint conventions), driver developers can work completely independently. They pick their language, their libraries, their deployment model. As long as the interface is right, the scheduler doesn't care what's behind it. This made onboarding new drivers fast and kept the team unblocked.

Every driver advertises itself via **Zeroconf (mDNS)**, so the scheduler discovers machines automatically — no hardcoded IPs, no central registry. Plug in a new machine, start its driver, and the scheduler picks it up. We wanted that plug-and-play experience because lab setups change constantly: equipment gets moved, new instruments arrive, things get swapped around.

## The driver plugin

Even though drivers *can* be written in any language, most of ours are in Python. To avoid rewriting the same boilerplate every time, I built a **shared FastAPI plugin** that all Python drivers inherit from. Call `create_app()` and you get:

- Health checks (`/health`, `/heartbeat`)
- Prometheus metrics (`/metrics`)
- Zeroconf advertisement
- Slot and plate state management
- First-boot configuration flow
- Structured logging and Sentry integration
- A consistent command/response model

A minimal driver looks something like this:

```python
from driver_plugin import create_app, Dimension

# Define the machine's geometry
slot = Dimension(label="slot", start=True, end=True, storage=True)
coordinates = slot() * 8  # 8 slots

app = create_app(
    machine_type="fridge",
    coordinates=coordinates,
)

@app.post("/commands/set-temperature")
async def set_temperature(target: float):
    # talk to hardware...
    return {"status": "ok", "temperature": target}
```

That's it. The plugin handles everything else. My colleagues could focus entirely on the hardware communication layer without worrying about discovery, health reporting, or state management.

### Why Python + FastAPI?

The team was already comfortable with Python — it's the lingua franca of biotech. FastAPI gave us automatic OpenAPI spec generation, which was critical: every driver exposes a machine-readable spec that the scheduler and tooling can introspect. The async support was also a natural fit for dealing with slow hardware operations.

But the key reason was the OpenAPI-first approach. Because our entire contract is defined by OpenAPI specs, we're not locked into Python. If someone wants to write a driver in Rust or Go tomorrow, they can — they just need to expose the right endpoints and advertise via mDNS.

### The Global Coordinate System

One of the trickier parts was modeling machine geometry in a generic way. A robot arm has a deck with carriers and slots. An incubator has shelves with positions. A liquid handler has a bed with racks.

I built a **Global Coordinate System (GCS)** — a tree of nested dimensions that can represent any machine layout:

```python
bed = Dimension(label="bed", start=True)
carrier = Dimension(label="carrier")
slot = Dimension(label="slot", stackable=True)
layer = Dimension(label="storage_layer", end=True, storage=True)

coordinates = bed([
    carrier([slot([layer(), layer()]), slot([layer(), layer()])]),
])
# Produces coordinates like: "carrier_A|slot_0|storage_layer_0"
```

Properties like `stackable`, `accessible`, and `storage` let the scheduler reason about where plates can go and which positions other machines can reach.

## The scheduler

The scheduler is the brain. It receives workflow submissions, breaks them down into tasks, steps, and commands, then dispatches commands to the right machines.

### Workflow execution model

Workflows follow a strict hierarchy:

- **Workflow** → contains **Tasks** (sequential)
- **Task** → contains **Steps** (sequential)
- **Step** → contains **Commands** (parallel, unless pinned to the same machine)

This gives scientists flexibility: steps run one after another for safety, but independent commands within a step run in parallel for speed.

### Machine selection

When a command needs a machine type (say, any available incubator) rather than a specific machine, the scheduler picks the one with the most free capacity that's currently idle. If the command involves a specific plate, only machines that have that plate loaded are considered. If nothing is available, the scheduler waits.

### Async command handling

Lab equipment is slow. A BLI run can last more than 10 hours. So commands are async by default:

::mermaid
---
code: |
  sequenceDiagram
    participant S as Scheduler
    participant D as Driver
    participant HW as Hardware
    S->>D: POST /commands/run-assay
    D-->>S: 202 Accepted + threadId
    D->>HW: Execute command
    Note over HW: Running...
    HW-->>D: Done
    D->>S: POST /api/event-hub (threadId + result)
    Note over S: Advance workflow
---
::

This keeps the scheduler non-blocking and lets it manage many machines concurrently. Getting the async coordination right was the hardest part of the whole project — managing concurrent workflows, handling race conditions when multiple experiments compete for the same machines, and making sure the system stays consistent when things go wrong.

### Failure handling

Not all failures are equal. A transient network glitch shouldn't kill a 4-hour experiment. So the system distinguishes between **soft failures** (retryable — the scheduler backs off and tries again) and **hard failures** (something is genuinely broken — the workflow pauses and an operator gets notified). The failure mode is determined by the driver, since it's the one that knows whether the error is recoverable.

Some hard failures are also handled directly at the workflow level — for example, a step can be marked as non-critical, so if it fails the workflow continues and the workcell isn't blocked. This is important in practice: you don't want an entire multi-hour experiment to halt because of a non-essential step.

### Slot mappings and plate tracking

Lab machines often share physical space — a robot arm's deck position A1 might correspond to an incubator's slot 3. **Slot mappings** define these relationships, so when the scheduler moves a plate from one machine to another, it knows which physical positions are paired.

Reservations are tracked per-execution and released when the workflow completes (or fails), preventing conflicts between concurrent experiments.

## The workflow builder

Scientists needed to create and iterate on workflows without touching code. I built a **visual workflow builder** using React Flow — a drag-and-drop node editor where users can compose experiments by wiring together tasks and steps.

Each node represents a task or command, and users configure parameters through forms. The builder knows which machines and commands are available (pulled from the OpenAPI specs), so it can offer auto-completion and validation. No YAML editing, no JSON schemas to learn — just drag, connect, configure, and submit.

This turned out to be one of the most impactful parts of the system. Scientists went from asking developers to code up new workflows to designing and iterating on them independently. The feedback loop went from days to minutes.

## The scheduler dashboard

For operators monitoring running experiments, I built a **real-time dashboard** that shows everything happening in the workcell:

- Live workflow execution progress (which step is running, what's next)
- Machine statuses (idle, busy, error, offline)
- Plate locations across all machines
- Execution logs and event history

Everything streams in real-time via Server-Sent Events (SSE), so the dashboard updates the moment something happens. No polling, no refresh button.

## driverctl — the CLI

Managing all of this in development and production needed good tooling. I built **driverctl**, a Typer-based CLI that handles the full lifecycle:

```bash
# Development
driverctl dev fridge              # Run with auto-reload
driverctl dev scheduler           # Launches dashboard too

# Discovery
driverctl list                    # Show all detected drivers
driverctl discover --workcell lab # mDNS scan

# Schema management
driverctl commands generate http://localhost:4242/openapi.json
driverctl commands list -m gator

# Production
driverctl build --all --out dist/
driverctl service install fridge  # Systemd service
```

It auto-discovers driver folders in the monorepo, handles port conflicts, bundles the dashboard with the scheduler, and generates systemd service files for production deployment. Basically everything you need to go from `git clone` to running a full workcell.

## Why not SiLA?

Before building anything, we looked at [SiLA 2](https://sila-standard.com/) — the industry standard for lab device communication. On paper it's exactly what you want: a standardized protocol so all lab equipment speaks the same language.

In practice, it didn't work for us. Most of the machines we were using (or planning to use) had no SiLA support at all. The few that did had poor or incomplete implementations. We would have spent more time fighting the standard than building our system.

So we went with our own stack, built on OpenAPI and mDNS — technologies we fully control and can iterate on quickly. And since our driver interface is just HTTP + OpenAPI, writing a SiLA v2 wrapper is trivial if we ever need one. We're not locked out of the ecosystem, we just chose not to start there.

## What I learned

**Design for independence.** The microservices + OpenAPI approach paid off beyond just the technical architecture. It let driver developers work autonomously — they just follow the guidelines, and their driver plugs right in. Organizational scalability matters as much as technical scalability.

**Zeroconf is underrated.** For a system where machines come and go, mDNS-based discovery was the right call. No central registry to maintain, no config files to update — things just find each other.

**Plugin architecture pays off fast.** The driver plugin was one of the first things I built, and it saved enormous amounts of time. Every new driver was a matter of hours instead of days, because all the boring infrastructure was already handled.

**Async-first is non-negotiable for hardware.** Lab equipment operates on its own timeline. Trying to do synchronous request/response with physical machines would have been a disaster. The callback-based model made everything much more robust — and getting the concurrency right was the hardest engineering challenge of the project.

**Build for non-technical users.** The workflow builder and dashboard made the system accessible to the people who actually use it. A powerful backend is useless if scientists still need a developer to run an experiment.

**Don't be afraid to skip the standard.** SiLA exists for good reasons, but it wasn't the right fit for us. Building our own system gave us full control and fast iteration speed, and the OpenAPI-based interface means we can always bridge to SiLA later if needed.
